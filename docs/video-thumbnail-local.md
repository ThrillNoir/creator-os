# Video thumbnail preparation (staging code, generator inactive)

The Library can save a private manual thumbnail through **Choose thumbnail**. `scripts/video-thumbnail-local.mjs` extracts one JPEG from a creator-scoped, verified H.264 or H.265 source with local FFmpeg/FFprobe. The temporary source copy is removed in `finally`. `scripts/video-thumbnail-storage-adapter.mjs` connects that extractor to injected D1 and R2 binding-shaped ports and offers a bounded per-creator dry run/batch operation. Neither module creates credentials, connects to Cloudflare on import, starts a schedule, or changes upload finalization. The Library now says “No thumbnail yet · Open to choose one” when a verified video has no poster.

The adapter loads the canonical D1 authority and storage-object row for the exact creator and asset, requires `canonical_verified`, and conditionally reads the matching private R2 object using its key, version and ETag. It does not rely on the uploader-supplied SHA as a server-verified checksum. It rechecks the same creator, asset, source revision, key, version, ETag and byte count, submits a bounded JPEG to the authenticated Web endpoint, which conditionally stores a content-addressed private JPEG and then uses a D1 compare-and-swap that sets `assets.preview_r2_key` only while still NULL and while the verified source identity is unchanged. R2 and D1 are separate stores, so this is not a cross-store transaction. An existing poster, including a manually chosen one, always wins. A failed compare-and-swap leaves the current poster untouched; a newly written orphan JPEG is retained for bounded later cleanup rather than risk deleting an image another concurrent job may have selected. Manual replacement remains available in the existing editor.

This module caps source size at 5 GiB, input frame size at 40 megapixels, output at 12 MiB, source idle time at 30 seconds and total source read time at 30 minutes. Extraction has a two-minute process timeout and two FFmpeg threads. The Mind runner caps a normal batch at two videos and 3 GiB, one at a time. Before a real run it needs enough private scratch disk for the full source and a constrained FFmpeg/FFprobe process; a scheduled run additionally needs monitoring and crash cleanup. A source object is read once per attempt; each successful source generates one private JPEG. The observed staging backlog was 22 verified H.265 videos without poster keys, about 3.2 GiB of source bytes with one about 2.3 GiB. Refresh this count before any backfill. No D1 migration is needed.

The remote R2 port honors the supplied `AbortSignal` and uses conditional GET by ETag. The adapter rejects missing or mismatched R2 version, ETag, or size before consuming the source. In-process cleanup removes temporary source files; a deployed timer must also clear stale scratch directories after crashes. A real R2 S3 response must be checked for `x-amz-version-id` against a synthetic object before the runner reads a creator original.

The tests use synthetic H.264/H.265 videos, in-memory SQLite with the real adapter SQL, mock R2 buckets, and mocked Cloudflare D1/R2 HTTP endpoints. They cover two creators, repeated runs, a manual-poster race, source revision and R2 identity changes, put failures, bounded dry runs, CLI gates, deterministic plan/receipt IDs, and scratch cleanup. `node scripts/verify-video-thumbnail-large.mjs` generates a synthetic HEVC file over 100 MiB and checks extraction without storage writes. These tests do not prove live Cloudflare transport, real R2/D1 consistency, or safe orphan garbage collection.

`scripts/video-thumbnail-mind-runner.mjs` provides a read-only `--plan --creator <id>`, an exact-plan `--apply <planId>`, and a callable `--tick` for a possible Mind timer. The remote D1 REST port permits only `SELECT`; it cannot write through the D1 API. Apply uses the staging Web endpoint, `/api/internal/video-thumbnail/commit`, for one creator-scoped, conditional poster-reference write. The endpoint validates the service principal and creator grant before accepting the bounded JPEG body, verifies JPEG format and dimensions, exact verified source and private poster bytes, and preserves a manual selection. It uses existing Web D1, LIBRARY_MEDIA, IMAGES and PREVIEWS bindings. The runner needs source-bucket ObjectRead only, not preview-bucket credentials. `scripts/video-thumbnail-keyring.mjs` reads named existing credentials in-process; its exact-plan apply still needs `THOT_THUMBNAIL_ALLOW_APPLY=1`. The Mind client sends both the internal service bearer and Cloudflare Access service credentials without following redirects. The JPEG-submitting endpoint was deployed to staging at commit `580cb1c`; the generator still has no service principal, Access credential or source R2 read credential. No timer or schedule is enabled. Workers' D1/R2 bindings do not provide FFmpeg to this local Node module. This candidate has not read real originals, written real R2/D1, or published media. The exact activation boundary is in `docs/video-thumbnail-release-plan.md`.

The batch returns `nextCursor` so the optional timer can advance past failed or over-budget assets instead of retrying the same first page forever. It resets the cursor after reaching the end and stores cursor state in a local 0600 file only if `--tick` is explicitly invoked. This is not a deployed schedule or durable cross-machine job ledger. An interrupted or uncertain R2/D1 outcome still needs operator reconciliation before any retry.
