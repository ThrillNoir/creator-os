# Video thumbnails: release plan

Status (2026-10-31): the JPEG-submitting Web endpoint is deployed to staging at commit `580cb1c`, Worker version `0efff9e7-05cc-4ffa-b492-281cf9a42320`. The generator is unactivated: no runner credentials, Adelaide-only service grant, timer, or real-media run exists. A local replay-integrity correction and hermetic test fix are not deployed. This document grants no deployment, access, or media-run permission.

## What exists locally

- An FFmpeg/FFprobe extractor handles verified H.264 and H.265 originals on the Mind and deletes temporary source copies. Large synthetic H.265 extraction was tested. Manual **Choose thumbnail** stays available and takes precedence.
- A bounded, creator-specific runner supports a read-only `--plan`, an exact-plan `--apply`, and a disabled optional `--tick`. Normal defaults are two items and 3 GiB of source bytes per invocation, processed sequentially. The executable is `scripts/video-thumbnail-mind-runner.mjs`; no schedule is installed.
- The Mind D1 REST port allows only `SELECT`. The only proposed D1 write goes through `POST /api/internal/video-thumbnail/commit` on the existing `thot-os-staging` Web Worker, using its `DB` and private `PREVIEWS` bindings. There is no generic SQL proxy, D1 Edit API token, or schema migration.
- The endpoint requires the existing Cloudflare Access boundary **and** an internal service bearer. It accepts only one operation: set a missing `assets.preview_r2_key` for an exact creator and asset. The existing service auth helper checks an active principal, credential, creator grant, and the `library.thumbnail.commit` capability. The endpoint verifies the canonical source key/revision/version/ETag/byte count and codec, the uploaded JPEG type and dimensions, server-derived private poster key, source R2 identity, and stored poster bytes and content hash. The runner cannot choose an arbitrary key. Its D1 compare-and-swap preserves a manual choice or changed source; replay is idempotent. It records a service audit event. The creator-scoped service principal is checked before reading the JPEG body; the JSON body is capped at roughly 16 MiB with a 30-second read deadline. The JPEG itself is capped at 12 MiB.
- The runner would read originals only from `thot-os-library-media-staging` with bucket-scoped ObjectRead. It submits the JPEG to the restricted Web endpoint; the Web Worker writes to `thot-os-previews-staging` through its existing private binding. No runner preview-bucket key is needed. It never rewrites source media. The generated poster is content-addressed, not another full-video copy.

No draft publication or public More change is part of this run.

The D1 database is also consumed by the live More publication control. A Web rollback does not undo D1/R2 poster changes. No timer, hosted FFmpeg service, full backlog, synthetic-data cleanup, or production resource change is included.

## Failure and cost limits

- Abort on missing/mismatched source version, ETag or byte count before downloading. After extraction, recheck source and poster state. A concurrent manual choice wins the conditional database update. A failed or uncertain commit is not blindly retried; inspect the asset and R2 object first.
- R2 and D1 are separate stores. A failed conditional update may leave an unreferenced private JPEG. A later bounded reference-checked cleanup needs its own plan; do not delete it immediately in a race.
- The run requires temporary disk space for the selected original, up to 5 GiB per file by implementation cap; the proposed first two use about 95.2 MB total. Output is capped at 12 MiB per poster. The run uses Mind CPU, R2 read/write operations, poster storage and D1 operations; it does not create durable full-video copies or enable a scheduled service. Review storage class and [R2](https://developers.cloudflare.com/r2/pricing/) and [D1](https://developers.cloudflare.com/d1/platform/pricing/) pricing before larger batches.
- The deployed Web Worker version is `0efff9e7-05cc-4ffa-b492-281cf9a42320` from commit `580cb1c`; the recorded previous version is `9e98be67-192a-47ba-8ef9-0e0d45b76d3e`. Any subsequent code correction needs a fresh exact release plan and rollback receipt. For rollback of a generated poster, first verify the exact key from the receipt and no later manual replacement. Clear only that reference with a reviewed conditional operation; retain the private object until no other reference exists. Code rollback alone cannot remove a stored poster.
